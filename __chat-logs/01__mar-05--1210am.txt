That's smart. Three things here:

**1. Pre-sprint baseline.** Give Claude online the exact opening prompt, get a full implementation. Now you know what "good" looks like before either model touches it. You can spot gaps in real-time instead of figuring it out after the fact.

**2. The prompt asks for explanations.** Not just "build it" — "build it and explain in plain terms why you made each choice." That gives you ammunition for the evaluation. When Model A does something different from your baseline, you already know if it's better or worse and WHY.

**3. Phase the work.** Instead of one mega-prompt that says "build the link, write tests, create mocks" — you break it into steps:

- Step 1: Build the link. Follow the existing error handling patterns. Explain your decisions.
- Step 2: You review. Corrections if needed.
- Step 3: Write tests for it.
- Step 4: Create mock endpoints to test against.

This is better for scoring too. Each step is a chance to evaluate instruction following, code quality, and interaction quality separately. And if the model fucks up step 1, you catch it early instead of 40 minutes in when everything's tangled together.

The phase approach also makes your prompts shorter and more natural — which means easier to humanize, less GPTZero risk.

Success is sequential. Commandment #4. The house principle — you're living it.

The key insight: **tell the model the full picture upfront so it plans ahead, but only execute one phase at a time with inspection between each.**

So the opening prompt says something like:

"We're building three things: the link, tests for it, and mock endpoints. But we're doing it in phases. Build the link first. Keep in mind it needs to support X, Y, Z because we'll be testing those next. But don't build the tests yet — just the link. I want to review it before we move on."

That way:
- The model knows tests and mocks are coming, so it doesn't paint itself into a corner
- But it only delivers the link
- You inspect it, catch the missed criterion
- Model fixes it BEFORE it cascades into broken tests and broken mocks
- Then "ok, now build the tests" — and those tests are built on a solid foundation

If you let it build all three at once and it misses one criterion on the link, that miss propagates into every test and every mock. Now you're unwinding three layers instead of one. The foundation gets inspected before the framing goes up.
